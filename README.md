# Invoice Expense Classification

A REST API that takes raw invoice text and returns the expense category it belongs to. Built with FastAPI and scikit-learn, it ships three model backends that you can switch between at request time — a fast TF-IDF pipeline for production use, a Naive Bayes baseline, and a Sentence Transformer model when accuracy matters more than latency.

---

## Why This Exists

Manually tagging invoices into expense categories is repetitive and error-prone at scale. This project wraps a trained text classifier behind a simple HTTP endpoint so any downstream system — ERP, finance dashboard, expense management tool — can classify invoice line items without human review.

The `/predict` endpoint accepts a plain text description and returns a category name plus a confidence score. That's it. No authentication, no complex request schemas, no vendor lock-in.

## Getting Started

### Prerequisites

- Python 3.10 or higher (tested on 3.13.5)
- pip
- An internet connection the first time you use the `transformer` model (downloads ~90 MB from HuggingFace; subsequent runs load from local cache)

### Local Setup

**1. Clone and create a virtual environment**

```bash
git clone https://github.com/SatAi999/Invoice-Expense-Classification.git
cd Invoice-Expense-Classification
python -m venv .venv
```

Activate it:

```bash
# Windows
.venv\Scripts\activate

# macOS / Linux
source .venv/bin/activate
```

**2. Install dependencies**

```bash
pip install -r requirements.txt
```

This pulls in FastAPI, scikit-learn, sentence-transformers, pandas, joblib, pytest, and httpx. Total install size including PyTorch (CPU) is around 1.5 GB.

**3. Train the models**

```bash
python scripts/train.py
```

Trains all three models sequentially, runs 5-fold cross-validation on each, prints a classification report, and saves the `.joblib` files to `models/`. Takes about 30 seconds on a laptop — most of that is the Sentence Transformer encoding step.

To train one specific model:

```bash
python scripts/train.py --model-type tfidf_lr
python scripts/train.py --model-type tfidf_nb
python scripts/train.py --model-type transformer
```

**4. Start the API**

```bash
uvicorn app.main:app --reload
```

The server starts on `http://localhost:8000`. If the `tfidf_lr.joblib` file is missing for some reason, the app will auto-train it on startup before accepting requests.

Interactive Swagger UI: `http://localhost:8000/docs`

## API Reference

### POST /predict

The main endpoint. Accepts invoice text, returns category and confidence.

**Request body**

```json
{
  "text": "Blue Dart courier charges for warehouse delivery"
}
```

**Response**

```json
{
  "category": "Logistics",
  "confidence": 0.871
}
```

The `confidence` value is the probability assigned by the classifier to the predicted class, on a 0 to 1 scale. Values above 0.8 are generally reliable; anything below 0.5 warrants human review.

**Selecting a model**

Pass the `model` query parameter to choose the backend:

```
POST /predict?model=tfidf_lr        (default)
POST /predict?model=tfidf_nb
POST /predict?model=transformer
```

Requesting an invalid model name returns HTTP 400 with a clear error message listing valid options.

---

**cURL**

```bash
# Default model
curl -X POST "http://localhost:8000/predict" \
  -H "Content-Type: application/json" \
  -d '{"text": "AWS EC2 monthly compute charges"}'

# Sentence Transformer model
curl -X POST "http://localhost:8000/predict?model=transformer" \
  -H "Content-Type: application/json" \
  -d '{"text": "AWS EC2 monthly compute charges"}'
```

**Python**

```python
import requests

url = "http://localhost:8000/predict"

examples = [
    "Blue Dart courier charges for warehouse delivery",
    "HP printer toner cartridge replacement",
    "AWS monthly cloud hosting bill",
    "Electricity bill for office premises March",
    "Air India flight tickets Mumbai to Delhi",
    "Steel sheets raw material purchase for factory",
]

for text in examples:
    resp = requests.post(url, json={"text": text})
    result = resp.json()
    print(f"{result['category']:<20} ({result['confidence']:.3f})  {text}")
```

Expected output:

```
Logistics            (0.871)  Blue Dart courier charges for warehouse delivery
Office Supplies      (0.716)  HP printer toner cartridge replacement
Cloud/Software       (0.851)  AWS monthly cloud hosting bill
Utilities            (0.728)  Electricity bill for office premises March
Travel               (0.688)  Air India flight tickets Mumbai to Delhi
Inventory            (0.929)  Steel sheets raw material purchase for factory
```

## The Three Models

All three models are trained on the same 491-row dataset and evaluated on the same 80/20 stratified split. Here is what the numbers look like:

| Model | CV Accuracy | Test Accuracy | Train Time | Inference |
|---|---|---|---|---|
| TF-IDF + Logistic Regression | 89.4% ± 4.0% | 88.9% | 65.9 ms | 9.5 µs/sample |
| TF-IDF + Naive Bayes | 84.3% ± 4.9% | 77.8% | 4.2 ms | 8.3 µs/sample |
| Sentence Transformer + LR | 92.9% ± 1.7% | 89.9% | 22.7 ms | ~6.4 ms/sample |

Full per-class breakdown is in `results/model_comparison.txt`.

---

### TF-IDF + Logistic Regression (`tfidf_lr`) — Default

The vectorizer uses unigrams and bigrams, 10,000 features, and sublinear TF scaling. Sublinear TF (`tf = 1 + log(tf)`) prevents common terms like "invoice" or "monthly" from dominating the feature space. The Logistic Regression uses `C=5.0` with the lbfgs solver.

This is the default because it has a good accuracy-to-latency ratio and the model file is small (under 2 MB). Under 10 microseconds per prediction means you can comfortably handle thousands of requests per second on a single core.

The model's main weakness is Utilities — it occasionally confuses utility bills with Office Supplies when the text is short and non-specific (e.g., "monthly service charge").

---

### TF-IDF + Naive Bayes (`tfidf_nb`) — Fast Baseline

Uses ComplementNB rather than MultinomialNB. ComplementNB trains each class using the complement of that class's data, which makes it more robust when class boundaries are not perfectly clean. Alpha is set to 0.1 (lighter smoothing than the sklearn default of 1.0, which works better here because the vocabulary is domain-specific and relatively dense).

At 4.2 ms total training time and 8.3 µs per inference, this is the fastest model. The accuracy cost is real though — Inventory drops to 52% recall on the test set, meaning roughly half of inventory invoices get misclassified. It would not be a good choice if Inventory is a high-volume category for you.

---

### Sentence Transformer + Logistic Regression (`transformer`) — Most Accurate

Uses `all-MiniLM-L6-v2` from the sentence-transformers library to encode each invoice description into a 384-dimensional dense vector, then feeds those embeddings into a Logistic Regression classifier. The encoder is not stored in the `.joblib` file — only the fitted LR weights are. On first load after startup, the encoder reloads from HuggingFace's local cache (~90 MB on disk).

The CV accuracy of 92.9% is the highest of the three, and crucially the standard deviation is much smaller (±1.7% vs ±4.0% for TF-IDF+LR). That consistency matters — it means the model generalises reliably rather than performing well on some folds and poorly on others.

The catch is the per-sample latency: encoding a single string through the transformer takes roughly 6 ms on CPU. That is fine for low-to-moderate traffic but will bottleneck at high request rates unless you batch requests or move to GPU inference.

## Model Comparison Script

Running `python scripts/compare_models.py` trains all three models fresh from the same train/test split, measures CV scores, timing, and per-class metrics, then writes a full report to `results/model_comparison.txt`. The report includes:

- 5-fold cross-validation accuracy and per-fold scores
- Test set accuracy (88/99, 77/99, 89/99 correct respectively)
- Classification report: precision, recall, F1 per category
- Confusion matrix for each model
- Summary table with best-value markers
- Recommendation for production vs accuracy-first use cases

## Docker

The Dockerfile pre-trains all three models at image build time, so container startup is instant with no training delay.

```bash
# Build and run with compose
docker compose up --build

# Or manually
docker build -t invoice-classifier .
docker run -p 8000:8000 invoice-classifier
```

The compose file includes a healthcheck that hits `/health` every 30 seconds. The API will be reachable at `http://localhost:8000` once the container reports healthy.

One thing to be aware of: building the image downloads PyTorch and sentence-transformers, which adds up to around 1.5 GB. The Transformer model weights (~90 MB) are also downloaded during the build. If you are building in a CI environment with no internet access, you will need to either bake the HuggingFace cache into the image or skip the transformer training step with `--model-type tfidf_lr`.

## Input Validation

The `/predict` endpoint rejects:

- Empty strings → HTTP 422 with `"text must not be empty"`
- Whitespace-only strings → same
- Missing `text` field → HTTP 422 (Pydantic)
- Oversized inputs are accepted; there is no hard length cap since invoice descriptions vary widely

Unknown fields in the request body are silently ignored (Pydantic's default behaviour).

## Extending the Project

**Adding a new category:** Add training rows to `data/training_data.csv`, re-run `python scripts/train.py`, and restart the API. No code changes needed — the categories are inferred from the data at training time.

**Swapping the transformer model:** Change `MODEL_NAME = "all-MiniLM-L6-v2"` in `app/model.py` to any sentence-transformers compatible model. Larger models like `all-mpnet-base-v2` will give better embeddings at the cost of more memory and slower encoding.

**Serving at scale:** The TF-IDF models are stateless and thread-safe. For the transformer model, consider batching requests and running multiple workers (`uvicorn --workers 4`). GPU acceleration will cut the per-sample encoding time from ~6 ms to under 1 ms.
